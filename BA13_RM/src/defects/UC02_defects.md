## 2. DEF-UC02-001 — Фантомная бронь в валидаторе duplicate-booking (**Exercise 04**, пункт 1 подпункт 1)

| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|

ID**                                    | `DEF-UC02-001`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **2. Краткое описание (что, где, когда?)**   | `17.04.2026` на стенде `staging` форма «Новая запись» при выборе клиента `Иванов И.И.` и слота `20.04.2026 14:00` у мастера `Петров А.В.` показывает предупреждение «У клиента уже есть бронь на этот слот», хотя в БД такой брони нет и клиент по телефону отрицает её существование.                                                                                                                                                                                                                                                                                                                                                                                                           |

| **4. Шаги воспроизведения**                  | 1. Открыть форму «Новая запись». 2. В поле «Клиент» ввести `Иванов` и выбрать `Иванов И.И.` из автокомплита. 3. В поле «Услуга» выбрать «Мужская стрижка». 4. В поле «Мастер» выбрать «Петров А.В.». 5. | **5. Ожидаемый результат (ОР)**              | После клика по свободному слоту форма остаётся в состоянии «готова к сохранению», никаких предупреждений о дубликате не появляется. Валидатор duplicate-booking должен вернуть `duplicate: false`, т.к. в БД нет конфликтующих броней клиента.                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| **6. Фактический результат (ФР)**            | В правом углу формы появляется жёлтый баннер «⚠ У клиента Иванов И.И. уже есть бронь на 20.04.2026 14:00 к мастеру Петров А.В. Подтвердите повторное бронирование?». Кнопка «Сохранить» заблокирована до подтверждения. В DevTools → Network: `POST /api/validate-booking` возвращает `200 OK` с `{"duplicate": true, "bookingId": null, "source": "cache"}`. **Отличие от ОР:** ложноположительное срабатывание валидатора — в БД брони нет, источник ответа — устаревший кэш.                                                                                                                                                                                                                   |
| **7. Постусловия (*)**                       | 1) Закрыть форму без сохранения. 2) Инвалидировать кэш валидатора: `POST /api/admin/cache/invalidate?scope=booking-validator`. 3) Перелогиниться менеджером `sidorovamp`. 4) Повторно открыть форму — предупреждение должно исчезнуть (если исправление выкачено) или остаться (если дефект активен).                                                                                                                                                                                                                                                                                                                                                                                            |
| **8. Окружение (*)**                         | macOS 14.5 · Chrome 123.0.6312.86 (arm64) · 1920×1080 @ 1x · Staging: `https://staging.barbershop.local` · API `1.0-sprint1` · Booking-service коммит `abc1234` · БД `postgres 15.4` · Redis 7.2 (кэш валидатора, TTL = 15 мин).                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **9. Приоритет (срочность исправления)**     | **Средний** — не блокирует бронирование полностью (менеджер может нажать «Подтверждаю» и продолжить), но создаёт шум и повышает вероятность человеческой ошибки.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| **10. Важность / критичность (*)**           | **Высокая** — вводит менеджера в заблуждение, рискует ошибочным отказом реальному клиенту или созданием дубликата из-за ложной уверенности «система уже знает об этом бронировании».                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **11. Описание (первопричина, гипотеза)**    | Валидатор `booking-validator` использует Redis-кэш `bookings:{clientId}:{date}` с TTL 15 мин, но при отмене/удалении брони (`DELETE /api/bookings/:id`) кэш **не инвалидируется** — только перезаписывается при создании новой брони. Слот `20.04.2026 14:00` был добавлен в кэш клиента `Иванов И.И.` при прогоне `TC-UC02-P-03` вчера; постусловие удалило запись из БД, но не дёрнуло кэш, и теперь валидатор отвечает «дубликат» на основании stale-ключа. Ожидаемая правка: добавить `cache.delete(key)` в обработчик `DELETE /api/bookings/:id` (booking-service, файл `bookings.service.ts:delete()`).                                                                                        |
| **12. Доп. материалы (скриншоты, логи)**     | 1) `def-001-phantom-warning.png` — скриншот жёлтого баннера в форме. 2) `def-001-network.har` — запись DevTools → Network с ответом `POST /api/validate-booking`. 3) `def-001-redis-key.txt` — дамп Redis: `redis-cli GET "bookings:CL-104:2026-04-20"` → `["14:00@EMP-010"]` (несуществующая бронь). 4) `def-001-app.log` — строки `booking-validator.ts:54` со `cache hit (stale=false)`. 5) Ссылка на тест-кейс: [`TC-UC02-P-01`](../test_cases/UC02_positive_test_cases.md#tc-uc02-p-01). |

## 3. DEF-UC02-002 — Lost update: слот не закрепляется за мастером после сохранения (**Exercise 04**, пункт 2 подпункт 2)

| Поле                                         | Значение                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **1. ID**                                    | `DEF-UC02-002`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                |
| **2. Краткое описание (что, где, когда?)**   | `17.04.2026` на стенде `staging` после нажатия «Сохранить» в форме «Новая запись» система создаёт запись `#501` и отвечает `HTTP 201 Created`, но слот `20.04.2026 14:00` мастера `Петров А.В.` **остаётся в списке свободных** и может быть повторно забронирован — нарушается бизнес-инвариант «один слот = одна запись».                                                                                                                                                                                                                                                                                                                                                                   |
| **3. Предусловие (*)**                       | 1) Предусловие `TC-UC02-P-01` выполнено. 2) Пройдены шаги 1–5 кейса (выбор клиента, услуги, мастера, слота, канала). 3) Предупреждение `DEF-UC02-001` подавлено кликом по «Подтверждаю» (для изолированной проверки checkpoint 2). 4) В соседней вкладке открыт `GET /api/slots?masterId=EMP-010&date=2026-04-20` для наблюдения состояния расписания в реальном времени.                                                                                                                                                                                                                                                                                                                       |
| **4. Шаги воспроизведения**                  | 1. На экране с заполненной формой нажать «Сохранить». 2. Дождаться ответа сервера (страница «Запись #501 создана»). 3. Во второй вкладке обновить `GET /api/slots?masterId=EMP-010&date=2026-04-20`. 4. В третьей вкладке открыть форму «Новая запись» для клиента `Петров К.Е.` и попытаться выбрать тот же слот `20.04.2026 14:00` у мастера `Петров А.В.`. 5. Нажать «Сохранить» во второй форме.                                                                                                                                                                                                                                                                                          |
| **5. Ожидаемый результат (ОР)**              | a) Страница «Запись #N создана», `N` > 0. b) `status = Confirmed` в карточке записи. c) Слот `14:00` **исчезает** из списка свободных в UI и в `GET /api/slots`. d) В очереди напоминаний появляется задача для канала `telegram` (FRQ002). e) Повторная попытка забронировать тот же слот во второй форме (шаг 4-5) получает `HTTP 409 Conflict` «Слот занят».                                                                                                                                                                                                                                                                                                                               |
| **6. Фактический результат (ФР)**            | a) Страница «Запись #501 создана» — ✔ есть. b) Статус = `Confirmed` — ✔. c) **Слот `14:00` остаётся в списке свободных** и в UI («Календарь мастера Петров А.В.»), и в ответе `GET /api/slots` (`14:00` → `free`). d) Задача на напоминание создана — ✔. e) **Повторная бронь успешно сохраняется** как запись `#502` → два Confirmed-бронирования на один слот (double-booking). **Отличие от ОР:** нарушены пункты (c) и (e) — бизнес-инвариант «один слот = одна запись» не выполняется.                                                                                                                                                                                                     |
| **7. Постусловия (*)**                       | 1) `DELETE /api/bookings/501` и `DELETE /api/bookings/502` от имени администратора. 2) Вручную через админ-панель перевести слот `20.04.2026 14:00` мастера `Петров А.В.` в статус `free` (если остался «занятым» из-за неконсистентности). 3) Перезапустить пул соединений booking-service: `POST /api/admin/db/reconnect`. 4) Проверить `GET /api/slots` — слот должен быть `free`.                                                                                                                                                                                                                                                                                                          |
| **8. Окружение (*)**                         | macOS 14.5 · Chrome 123.0.6312.86 · 1920×1080 · Staging `https://staging.barbershop.local` · API `1.0-sprint1` · Booking-service коммит `abc1234` · БД `postgres 15.4` (read-committed) · Транспорт: HTTP/1.1, средний RTT до backend ≈ 80 мс (воспроизводится стабильнее при искусственном лаге 500 мс между шагами).                                                                                                                                                                                                                                                                                                                                                                        |
| **9. Приоритет (срочность исправления)**     | **Высокий** — прямое нарушение бизнес-правила и ожидаемого поведения UC02 (постусловие основного потока, FRQ001). Блокирует фичу для production.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| **10. Важность / критичность (*)**           | **Критическая** — возможна двойная продажа одного слота двум разным клиентам, что приводит к репутационному и финансовому ущербу барбершопа.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  |
| **11. Описание (первопричина, гипотеза)**    | В `BookingService.create()` сейчас две независимые транзакции: (T1) `INSERT INTO bookings (...)` в booking-service, (T2) `UPDATE master_schedule SET slot_status='occupied' WHERE id=?` в schedule-service, вызов идёт через `HTTP PATCH /api/schedule/slots/:id` **после коммита T1**. Между T1 и T2 нет двухфазного коммита, нет саги, нет блокировки `SELECT ... FOR UPDATE` на слоте. При любом сбое (таймаут, 5xx, рестарт pod-а) T2 теряется — T1 остаётся, запись создана, слот «свободен». Воспроизводится детерминированно при добавлении 500 мс лагу между T1 и T2 через `toxiproxy`. Ожидаемая правка: перевести операции в одну распределённую транзакцию (сага с компенсацией). |
| **12. Доп. материалы (скриншоты, логи)**     | 1) `def-002-calendar-free-slot.png` — скриншот календаря мастера: `14:00` всё ещё зелёный. 2) `def-002-slots-response.json` — сохранённый JSON `GET /api/slots` после шага 3. 3) `def-002-booking-service.log` — строки `BookingService.ts:create():142` успешный INSERT, затем `ScheduleClient.ts:patch():58` `TimeoutError after 500ms`. 4) `def-002-double-booking.mp4` — видеозапись создания брони `#502` на тот же слот. 5) Ссылка на тест-кейс: [`TC-UC02-P-01`](../test_cases/UC02_positive_test_cases.md#tc-uc02-p-01). |
