## 1. Стратегия негативного покрытия

| Категория        | Что проверяем                                                     | Кейс            |
| ---------------- | ----------------------------------------------------------------- | --------------- |
| Race / concurrency | Слот был занят после открытия формы, но до сохранения           | `TC-UC02-N-01`  |
| UI / валидация   | Обязательное поле оставлено пустым                                | `TC-UC02-N-02`  |
| Формат ввода     | Невалидный телефон при создании клиента «на лету»                 | `TC-UC02-N-03`  |
| Бизнес-правило   | Выбранный мастер не оказывает выбранную услугу                    | `TC-UC02-N-04`  |
| Граница времени  | Выбранный слот уже в прошлом (наступил/прошёл)                    | `TC-UC02-N-05`  |

Менеджер-персона для всех кейсов — та же: `EMP-003` Сидорова М. П., роль = manager
(см. «UC02 positive» п. 1.3).

Все кейсы удовлетворяют:
- **F.I.Repeatable.S.T.** — состояние окружения полностью восстанавливается постусловием (ничего в БД не коммитится, либо откатывается);
- **F.Independent.S.T.** — каждый кейс использует собственные слоты/клиентов/мастеров, между кейсами порядок не важен.

## 3. TC-UC02-N-01 — Попытка записи на занятый слот (stale UI)

| Поле                  | Значение                                                                                                                                         |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **1. ID**             | `TC-UC02-N-01`                                                                                                                                   |
| **2. Название**       | Запись на слот, который был занят другим каналом после открытия формы (race)                                                                     |
| **3. Приоритет**      | Высокий                                                                                                                                          |
| **4. Предусловие**    | 1) Менеджер `sidorovamp` авторизован. 2) В БД есть клиент `Иванов И. И., +7 999 123 45 67`. 3) У мастера «Петров А.В.» на `20.04.2026 14:00` слот свободен, услуга — «Мужская стрижка». 4) Вкладка менеджера с формой «Новая запись» уже открыта ≥ 30 с назад (список слотов закеширован). 5) Через вторую сессию (онлайн-клиент или другой менеджер) слот `14:00` забронирован и зафиксирован в БД. |
| **5. Менеджер**       | `EMP-003` · Сидорова Мария Петровна · роль = manager                                                                                             |
| **6. Шаги**           | 1. В исходной (старой) форме менеджера выбрать клиента `Иванов И.И.`. 2. Услуга = «Мужская стрижка». 3. Мастер = «Петров А.В.». 4. В устаревшем календаре выбрать слот `20.04.2026 14:00` (по кешу формы слот ещё свободен). 5. Канал связи = «Telegram». 6. Нажать «Сохранить». |
| **7. Ожидаемый результат (ОР)** | a) Система возвращает HTTP 409 Conflict с текстом `«Слот занят. Обновите расписание и выберите другой слот»`. b) Запись `N` **не** создаётся (`SELECT COUNT(*) FROM bookings WHERE ...` — без изменений). c) Форма предлагает кнопку «Обновить расписание»; после клика слот `14:00` исчезает из списка свободных. d) В очереди напоминаний — без изменений. |
| **8. Постусловие**    | Закрыть форму; удалить бронирование, сделанное во второй сессии (`DELETE /api/bookings/<id_второй_сессии>`); убедиться, что слот `14:00` снова свободен. |
| **9. Фактический результат (ФР)** | _Pending — заполнить после прогона._                                                                                                             |
| **10. Повторяемость** | ✓ Двойной setup детерминирован: оба шага (открыть форму в одной сессии + занять слот во второй) выполнимы скриптом `seed_race.sh`; постусловие возвращает слот. |
| **11. Атомарность**   | ✓ Кейс работает со своим слотом (`Петров · 14:00`); другие негативы используют других мастеров/слотов.                                           |

| **1. ID**             | `TC-UC02-N-04`                                                                                                                                   |

| **3. Приоритет**      | Средний                                                                                                                                          |

| **5. Менеджер**       | `EMP-003` · Сидорова Мария Петровна · роль = manager                                                                                             |
| **6. Шаги**           | 1. Открыть «Новая запись». 2. Клиент = `Орлов Н.Н.`. 3. Услуга = «Окрашивание бороды». 4. Если UI корректен — мастер «Петров А.В.» должен быть недоступен в списке. Попытаться выбрать его через прямой URL-параметр `?masterId=<Петров>`. 5. Слот = `12:00`. 6. Канал связи = «VK». 7. Нажать «Сохранить». |
| **7. Ожидаемый результат (ОР)** | a) Если API получил запрос — возвращается HTTP 422 с телом `{"error":"MASTER_DOES_NOT_PROVIDE_SERVICE","masterId":"...","serviceId":"..."}`. b) Запись `N` не создаётся. c) Слот `12:00` у Петрова остаётся свободен. d) На UI — сообщение `«Мастер не выполняет выбранную услугу. Выберите другого мастера.»`. |
| **8. Постусловие**    | Закрыть форму; `SELECT COUNT(*) FROM bookings WHERE master='Петров А.В.' AND dt='2026-04-20 12:00'` → 0.                                         |
| **9. Фактический результат (ФР)** | _Pending — заполнить после прогона._                                                                                                             |
| **10. Повторяемость** | ✓ БД не меняется, тестовые данные (`master_services` без записи «Петров × Окрашивание») создаются миграцией сида.                                |
| **11. Атомарность**   | ✓ Собственный слот Петрова (12:00) — не совпадает со слотом `14:00` в N-01.                                                                      |
